# MINK Interoperability Roadmap

**Version:** 0.1.0 (Design Draft)
**Date:** August 25, 2026
**Status:** DESIGN ONLY — not implemented
**Scope:** Long-term interoperability stack for MINK with other languages

---

## 1. Goals

1. **Universal interop.** MINK must work alongside Python, C++, C#, Rust, and other languages.

2. **C ABI as the universal bridge.** All language interop goes through the C ABI. No native bridges per language.

3. **Zero-copy where possible.** Data sharing between languages should avoid unnecessary copies.

4. **Safety at the boundary.** Ownership and lifetime safety are enforced at the C ABI boundary.

5. **AI-friendly.** Binding generation is automated and machine-readable.

---

## 2. Interoperability Stack

```
MINK
├── C ABI (universal bridge)
│   ├── C (native)
│   ├── C++ (via C ABI)
│   ├── Python (via CPython extension)
│   ├── C# (via P/Invoke)
│   ├── Rust (via C ABI)
│   ├── Go (via cgo)
│   ├── Java (via JNI)
│   └── other languages
├── Binding generation
│   ├── mink bind --target c
│   ├── mink bind --target c++
│   ├── mink bind --target python
│   ├── mink bind --target csharp
│   ├── mink bind --target rust
│   └── mink bind --target go
└── Runtime library
    ├── mink_str_free()
    ├── mink_vec_free()
    └── mink_panic_handler()
```

## 3. Python Integration

### Integration model: CPython extension module

```
mink_python/
├── src/
│   ├── mink_module.c   # CPython module definition
│   └── mink_bridge.c   # C ABI bridge
├── mink.toml           # MINK package
└── setup.py            # Python build
```

### MINK → Python
- MINK compiled library callable from Python via C ABI
- Python wrapper generated by `mink bind --target python`
- Shipped as Python wheels with platform-specific MINK binaries

### Python → MINK
- Python calls MINK functions through CPython extension module
- Arguments marshaled through C ABI
- Return values marshaled back to Python

### Buffer sharing (zero-copy)

| Scenario | Can be zero-copy? | Requires |
|----------|------------------|----------|
| NumPy array → MINK | Yes (read-only) | Pointer sharing, lifetime contract |
| MINK buffer → Python | Yes (read-only) | Pointer sharing |
| MINK string → Python | No | Copy (different representations) |
| Complex objects | No | Serialization |

### NumPy interoperability

```python
import mink_math
import numpy as np

# Zero-copy: NumPy array shared with MINK
arr = np.array([1.0, 2.0, 3.0])
result = mink_math.dot_product(arr)  # Zero-copy read
```

### Buffer protocol

```c
// MINK exported function for buffer sharing
typedef struct {
    uint64_t len;
    const void *ptr;
} MinkBuffer;

// Python buffer protocol support
MinkBuffer mink_get_data() {
    return (MinkBuffer){ .len = data_len, .ptr = data_ptr };
}
```

### PyTorch tensor interoperability (V3+)

```python
import mink_ml
import torch

# Zero-copy: PyTorch tensor shared with MINK
tensor = torch.randn(100, 100)
result = mink_ml.matrix_multiply(tensor)  # Zero-copy read
```

### Ownership/lifetime safety
- Python must not use MINK-allocated data after the MINK function returns
- MINK must not use Python-allocated data after the Python function returns
- Lifetime contracts are documented per-function
- Reference counting is managed by the CPython extension module

## 4. C++ Integration

### Model: C ABI bridge with C++ wrappers

```
MINK compiled library (.dll/.so)
        ↓
C ABI header (generated)
        ↓
C++ wrapper classes (generated or hand-written)
        ↓
C++ application
```

### MINK → C
- Export functions with `#[export]` attribute
- C ABI calling convention
- Header generation from MINK source

### C → MINK
- Declare external functions with `extern "C"`
- Call MINK functions using C ABI
- Link against MINK compiled library

### MINK → C++
- Same as MINK → C (use `extern "C"` for the ABI)
- C++ wrapper layer for type safety
- RAII wrappers for MINK resources

### C++ → MINK
- Wrap C ABI calls in C++ classes
- Provide header files with type-safe wrappers

### Generated C++ header

```cpp
// Generated by mink bind --target c++
#ifndef MINK_LIB_HPP
#define MINK_LIB_HPP

#include <cstdint>
#include <string>
#include <vector>

extern "C" {
#include "lib.h"
}

namespace mink {

class Str {
    MinkStr raw_;
public:
    Str(const char* s) : raw_{ strlen(s), reinterpret_cast<const uint8_t*>(s) } {}
    Str(const std::string& s) : raw_{ s.size(), reinterpret_cast<const uint8_t*>(s.data()) } {}
    ~Str() { mink_str_free(raw_); }
    
    std::string to_string() const {
        return std::string(reinterpret_cast<const char*>(raw_.ptr), raw_.len);
    }
    
    const MinkStr& raw() const { return raw_; }
};

int64_t add(int64_t a, int64_t b) {
    return mink_main_add(a, b);
}

} // namespace mink

#endif // MINK_LIB_HPP
```

### Struct layout compatibility
- MINK structs use C-compatible layout (`#[repr(C)]` equivalent)
- C++ can directly use MINK structs as value types
- Nested structs are supported

### RAII compatibility

```cpp
// RAII wrapper for MINK-allocated memory
class MinkGuard {
    MinkStr data_;
public:
    MinkGuard(MinkStr s) : data_(s) {}
    ~MinkGuard() { mink_str_free(data_); }
    
    // Non-copyable, movable
    MinkGuard(const MinkGuard&) = delete;
    MinkGuard& operator=(const MinkGuard&) = delete;
    MinkGuard(MinkGuard&& other) noexcept : data_(other.data_) { other.data_ = {0, nullptr}; }
    MinkGuard& operator=(MinkGuard&& other) noexcept;
};
```

### Exception boundary
- C++ exceptions must not cross into MINK
- MINK errors must not cross into C++ as exceptions
- The boundary translates between error models:
  - MINK `Result<T,E>` → C++ exception (optional wrapper)
  - C++ exception → MINK error code (optional wrapper)

## 5. C# Integration

### Model: P/Invoke with generated bindings

```
MINK compiled library (.dll, C ABI)
        ↓
C# P/Invoke declarations (generated)
        ↓
.NET application
```

### Blittable type mapping

| MINK | C# | Notes |
|------|-----|-------|
| `Int` | `long` | 64-bit signed |
| `Bool` | `byte` | 0/1 |
| `Float` | `double` | IEEE 754 |
| `Char` | `byte` | Single byte |
| `Str` | `IntPtr` + length | Manual marshaling |
| `Ptr<T>` | `IntPtr` | Raw pointer |
| `Struct` | Blittable struct | Same layout |

### Generated C# bindings

```csharp
// Generated by mink bind --target csharp
using System;
using System.Runtime.InteropServices;

namespace Mink
{
    [StructLayout(LayoutKind.Sequential)]
    public struct MinkStr
    {
        public ulong Len;
        public IntPtr Ptr;
    }
    
    public static class Native
    {
        private const string LibName = "mink_package";
        
        [DllImport(LibName, CallingConvention = CallingConvention.Cdecl)]
        public static extern long mink_main_add(long a, long b);
        
        [DllImport(LibName, CallingConvention = CallingConvention.Cdecl)]
        public static extern void mink_str_free(MinkStr s);
    }
    
    public static class MinkString
    {
        public static string FromMink(MinkStr s)
        {
            return Marshal.PtrToStringUTF8(s.Ptr, (int)s.Len);
        }
        
        public static MinkStr ToMink(string s)
        {
            var ptr = Marshal.StringToHGlobalAnsi(s);
            return new MinkStr { Len = (ulong)s.Length, Ptr = ptr };
        }
    }
}
```

### SafeHandle pattern

```csharp
// SafeHandle for MINK resources
public class MinkStringHandle : SafeHandle
{
    public MinkStringHandle(MinkStr str) 
        : base(IntPtr.Zero, ownsHandle: true)
    {
        handle = str.Ptr;
        _length = str.Len;
    }
    
    public override bool IsInvalid => handle == IntPtr.Zero;
    
    protected override bool ReleaseHandle()
    {
        Native.mink_str_free(new MinkStr { Len = _length, Ptr = handle });
        return true;
    }
}
```

### P/Invoke considerations
- Blittable types are marshaled directly (no copy)
- Non-blittable types require manual marshaling
- String marshaling uses `UnmanagedType.LPStr` or manual `IntPtr`
- Array marshaling uses `MarshalAs` attributes

## 6. Rust Integration

### Model: C ABI bridge (NOT direct Rust type sharing)

**Why C ABI, not direct Rust types:**
- MINK and Rust have different ownership models
- Rust's `unsafe` boundaries would leak into MINK
- C ABI is simpler and more portable
- Rust has excellent C FFI support

### Binding generation

```bash
mink bind --target rust src/lib.mink > mink_bindings.rs
```

### Generated Rust code

```rust
// Generated by mink bind --target rust
#![allow(non_camel_case_types)]

#[repr(C)]
pub struct MinkStr {
    pub len: u64,
    pub ptr: *const u8,
}

impl MinkStr {
    pub fn to_str(&self) -> &str {
        unsafe {
            let slice = std::slice::from_raw_parts(self.ptr, self.len as usize);
            std::str::from_utf8_unchecked(slice)
        }
    }
}

impl Drop for MinkStr {
    fn drop(&mut self) {
        unsafe { mink_str_free(*self); }
    }
}

#[repr(C)]
pub struct MinkVec {
    pub capacity: u64,
    pub length: u64,
    pub elements: *const std::ffi::c_void,
}

extern "C" {
    pub fn mink_main_add(a: i64, b: i64) -> i64;
    pub fn mink_str_free(s: MinkStr);
    pub fn mink_vec_free(v: MinkVec);
}

// Safe Rust wrapper
pub fn add(a: i64, b: i64) -> i64 {
    unsafe { mink_main_add(a, b) }
}
```

### Ownership safety
- `MinkStr` implements `Drop` to call `mink_str_free`
- `MinkVec` implements `Drop` to call `mink_vec_free`
- Rust's ownership model ensures no double-free or use-after-free
- The `unsafe` block is contained within the generated bindings

## 7. Go Integration

### Model: cgo

```go
package mink

/*
#cgo LDFLAGS: -L. -lmink_package
#include "mink_lib.h"
*/
import "C"

func Add(a int64, b int64) int64 {
    return int64(C.mink_main_add(C.int64_t(a), C.int64_t(b)))
}
```

### Binding generation

```bash
mink bind --target go src/lib.mink > mink_bindings.go
```

### Go-specific considerations
- Go uses cgo for C FFI
- Go garbage collector does not manage MINK memory
- Lifetime contracts must be documented
- Go strings must be converted to `MinkStr` before passing

## 8. Java Integration

### Model: JNI (Java Native Interface)

```java
public class MinkNative {
    static {
        System.loadLibrary("mink_jni");
    }
    
    public static native long add(long a, long b);
}
```

### Binding generation

```bash
mink bind --target java src/lib.mink > MinkNative.java
mink bind --target jni src/lib.mink > mink_jni.c
```

### JNI considerations
- JNI is complex and verbose
- Lifetime management is critical (local vs global references)
- String marshaling requires care
- Consider using a simpler bridge (e.g., JNA) for V1

## 9. Cross-Language Data Sharing

### Shared data formats

| Format | Use case | Zero-copy? |
|--------|----------|------------|
| Raw bytes | Binary data | Yes (read-only) |
| JSON | Structured data | No (parse/serialize) |
| FlatBuffers | Performance-critical | Yes (read-only) |
| Protocol Buffers | Schema-driven | No (parse/serialize) |

### Buffer sharing protocol

```c
// Shared buffer type
typedef struct {
    uint64_t len;
    const void *ptr;
    uint64_t element_size;
    uint32_t flags;  // READ_ONLY, ZERO_COPY, etc.
} SharedBuffer;
```

### Ownership rules for shared data
1. **Read-only sharing:** Both sides can read, neither can write
2. **Exclusive access:** One side owns the data, the other borrows
3. **Transfer:** Ownership transfers from one side to the other
4. **Reference counting:** Both sides share ownership (V3+)

## 10. Binding Generation Tool

### `mink bind` command

```bash
mink bind --target <language> <source.mink> > <output>
```

### Supported targets

| Target | Language | Output format |
|--------|----------|---------------|
| `c` | C | `.h` header file |
| `c++` | C++ | `.hpp` header file |
| `python` | Python | `.py` wrapper |
| `csharp` | C# | `.cs` bindings |
| `rust` | Rust | `.rs` bindings |
| `go` | Go | `.go` bindings |
| `java` | Java | `.java` + `.c` JNI |

### Binding generation rules
1. Only `#[export]` functions are included
2. Types are mapped to target-language equivalents
3. Doc comments become target-language documentation
4. Ownership rules are documented per-function
5. Safety warnings are included where applicable

## 11. Two-Approach Analysis

### Approach A: C ABI as primary FFI boundary (CHOSEN)

| Criterion | Assessment |
|-----------|------------|
| **Pros** | Universal support, simple implementation, proven at scale |
| **Cons** | Some overhead for complex types, no type-safe ownership crossing |
| **Complexity** | Low-Medium |
| **Performance** | Good for most use cases |
| **Security** | Clear boundary, explicit ownership rules |
| **Compatibility** | Universal — works with all target languages |
| **Maintainability** | One ABI to maintain, not N |
| **Ecosystem impact** | Maximum — every language can interoperate |

### Approach B: Native ABI with language-specific bridges

| Criterion | Assessment |
|-----------|------------|
| **Pros** | Zero-overhead for specific languages, richer type information |
| **Cons** | N implementations for N languages, massive maintenance burden |
| **Complexity** | High |
| **Performance** | Optimal for specific pairs, worse overall |
| **Security** | More attack surface per bridge |
| **Compatibility** | Good for target languages, poor for others |
| **Maintainability** | High burden — each bridge needs testing and versioning |
| **Ecosystem impact** | Fragmented — only well-supported languages benefit |

### Decision: **Approach A**

**Reasoning:** MINK's strategic goal is interoperability with ALL major languages. C ABI covers 95% of use cases. The 5% overhead for complex types is acceptable. The maintenance burden of N bridges would be catastrophic for a small team. C ABI is the universal adapter.

## 12. Implementation Priority

### Phase 1: C ABI foundation (V1.x)
- C header generation (`mink bind --target c`)
- Exported functions with `#[export]`
- Imported functions with `extern "C"`
- Deallocation functions (`mink_str_free`, `mink_vec_free`)

### Phase 2: C++ wrappers (V2)
- C++ header generation (`mink bind --target c++`)
- RAII wrappers for MINK resources
- Exception boundary translation

### Phase 3: Python integration (V2+)
- CPython extension module bridge
- Buffer sharing (zero-copy for read-only data)
- Python wrapper generation (`mink bind --target python`)

### Phase 4: C# integration (V3)
- P/Invoke binding generation (`mink bind --target csharp`)
- SafeHandle wrappers
- Blittable type mapping

### Phase 5: Rust integration (V3)
- Rust binding generation (`mink bind --target rust`)
- Ownership safety wrappers

### Phase 6: Go integration (V4)
- cgo binding generation (`mink bind --target go`)

### Phase 7: Java integration (V4+)
- JNI binding generation (`mink bind --target java`)
