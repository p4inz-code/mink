# MINK brand assets and Windows file identity

**Status:** implemented · **Version:** 1.0.4 at implementation (unchanged by
the 1.0.5 candidate) · **Platform:** Windows x86_64
**Design source:** the supplied `MINK UI SETS OFFICIAL` artwork package (2026-10-25), used as
delivered — no artwork was redrawn, recoloured or rescaled.

This page documents what was integrated, where it lives, how the `.mink` Windows file
association is registered and removed, and what is deliberately *not* integrated. The
implementation record with the validation transcript is
[`docs/implementation/SESSION_139_BRAND_ASSETS_WINDOWS_FILE_IDENTITY.md`](../implementation/SESSION_139_BRAND_ASSETS_WINDOWS_FILE_IDENTITY.md).

## 1. Where the artwork lives

| Path | Contents |
| --- | --- |
| [`assets/brand/`](../../assets/brand/) | the repository's authoritative brand tree (116 files): source masters, logo variants, icons, web/GitHub assets, previews |
| [`npm/mink/windows/`](../../npm/mink/windows/) | the only copy that ships to users: the registration script, both ICOs, `mink.rc`, a short README |
| `README.md` | uses `assets/brand/web/github/mink-readme-header-{light,dark}.png` |

`assets/brand/README.md` lists every directory, the colourways, the size rules and the
files that are intentionally absent. Nothing in the brand tree is generated by the build.

## 2. Logo variants

Three colourways exist for every lockup: `-ink` (`#1C1D21`, the default on light
backgrounds), `-white` (for dark backgrounds) and `-black` (`#000000`, for print and
one-colour production). Lockups: primary (stacked), horizontal, compact, symbol and
wordmark; the symbol additionally has an optical-small variant for 64–128 px and a
silhouette variant for 64 px and below. Palette: Ink `#1C1D21`, White `#FFFFFF`,
Fold `#3A3C44`, Edge `#45474F`, Paper `#F4F4F2`.

The horizontal lockup has a minimum width of 96 px / 20 mm and clear space equal to the
wordmark cap-height, already built into the SVG bounds. The README header uses the
supplied 1280x320 PNG pair through a `<picture>` element so it follows the reader's
colour scheme.

## 3. Application icon and `mink.exe`

`assets/brand/windows/ico/mink-app.ico` (shipped as `npm/mink/windows/mink-app.ico`) is
the official application icon: 7 frames — 16, 24, 32, 48, 64, 128 and 256 px — all 32-bpp
PNG-compressed, and each frame is byte-identical to the PNG export it was built from
(`assets/brand/icon/application/png/`).

**Limitation: `mink.exe` carries no icon resource.** The compiler binary is produced by
`cargo build` with zero crate dependencies and no build script, which is a documented
property of the project. Embedding an icon means compiling a resource script with
`rc.exe`/`windres` and adding the object to the link; that would

1. add an external toolchain prerequisite to a build that deliberately has none, and
2. make the content of the released binary depend on the machine that built it, while
   [`docs/implementation/SESSION_121_V1_0_4_RELEASE.md`](../implementation/SESSION_121_V1_0_4_RELEASE.md)
   records a verified SHA-256 for the released artifact.

The integration therefore stops at the distribution layer instead of changing the build:
the ICO is shipped next to the compiler, and `mink.rc` (with corrected icon paths) is
provided for anyone who wants to embed it locally:

```bat
rc /fo mink.res mink.rc            :: MSVC, from npm\mink\windows
windres mink.rc -O coff -o mink.res.o   :: MinGW
```

What users see today: `mink.exe` keeps the default executable icon, while `.mink` source
files carry the MINK identity through the file association below. `mink-app.ico` is still
useful on shortcuts, in installers and as the icon of a future editor extension.

## 4. `.mink` source-file icon

`assets/brand/windows/ico/mink-file.ico` (shipped as `npm/mink/windows/mink-file.ico`)
is the `.mink` source-file icon, distinct from the application icon by design: a document
sheet carrying the mink mark, with the wordmark only in the 128 and 256 px frames. It has
the same 7 frames and is likewise byte-identical frame-for-frame to
`assets/brand/icon/source-file/png/`. A one-colour variant
(`icon/source-file/mink-file-mono.svg`) and a 1024 px PNG are in the brand tree for
editor and print use.

## 5. The `.mink` Windows file association

| Property | Value |
| --- | --- |
| Extension | `.mink` |
| ProgID | `MINK.SourceFile` |
| Display name | `MINK Source File` |
| Content type | `text/x-mink` |
| Perceived type | `text` |
| Default icon | `mink-file.ico` (quoted path, index 0) |
| Default action | **none** — Windows' normal "Open with" flow |
| Scope | per-user (`HKCU`), no administrator rights, `HKLM` untouched |

Registry layout written by the script:

| Key | Value |
| --- | --- |
| `HKCU\Software\Classes\.mink` | `(default)` = `MINK.SourceFile`, `Content Type`, `PerceivedType` |
| `HKCU\Software\Classes\MINK.SourceFile` | `(default)` and `FriendlyTypeName` = `MINK Source File` |
| `HKCU\Software\Classes\MINK.SourceFile\DefaultIcon` | `"<install>\mink-file.ico",0` |
| `HKCU\Software\Classes\MINK.SourceFile\shell\open\command` | only with `-Editor`: `"<editor.exe>" "%1"` |
| `HKCU\...\Explorer\FileExts\.mink\OpenWithProgids` | `MINK.SourceFile` (REG_NONE), so the type appears in the Open-with list |

**Double-clicking a `.mink` file never compiles or runs it.** No `open` verb is
registered by default, so the shell cannot execute anything for the type: Windows shows
its normal picker, the user's answer is remembered by Windows in the user-owned
`FileExts\.mink\UserChoice`, and MINK never becomes the handler of its own source files.
To bind one editor explicitly, pass `-Editor`; the command is then the editor applied to
the file, with both paths quoted.

**Taking `.mink` over from another application.** If another ProgID currently owns
`.mink`, registration refuses and changes nothing until `-Force` is given. `-Force`
records the previous owner in `MINK.SourceFile\PreviousDotMinkOwner` and `-Uninstall`
restores it. A class-level `OpenWithProgids` list created by that other application is
never deleted: while it exists Windows treats the extension as "open with" and asks the
user to confirm the application once, which is the documented shell behaviour.

**Uninstall removes only MINK-owned entries**: the extension's default value only if it is
still `MINK.SourceFile`, the `Content Type`/`PerceivedType` values only if they are the
ones this integration wrote, the `MINK.SourceFile` tree, and the `OpenWithProgids` value
under `FileExts`. Another application's values and subkeys inside `HKCU\Software\Classes\.mink`
are preserved, the `UserChoice` default-app entry is never touched, and an extension key
that is empty afterwards is removed so no debris is left.

**Shell refresh** uses `SHChangeNotify(SHCNE_ASSOCCHANGED, SHCNF_IDLIST, NULL, NULL)` and,
when present, `ie4uinit.exe -show` to rebuild the cached file-type icon. Explorer is never
restarted or killed.

**Why one mechanism.** The design package also contains a `.reg` file and an Inno Setup
snippet. Neither is shipped: a `.reg` file cannot resolve an installation path, so it has
to hard-code one (the supplied reference assumes
`%LOCALAPPDATA%\Programs\MINK\bin`, which this repository does not provide) and it
hard-coded Notepad as the open command; the Inno Setup snippet belongs to an installer
that does not exist. The PowerShell script is the single authoritative mechanism.

## 6. Register and unregister

The shipped package resolves everything from its own location, so any npm prefix, drive
or Unicode path works:

```powershell
$package = Join-Path (npm root -g) '@p4inz-code\mink'
powershell -ExecutionPolicy Bypass -File "$package\windows\register-mink-filetype.ps1"            # register
powershell -ExecutionPolicy Bypass -File "$package\windows\register-mink-filetype.ps1" -Uninstall # remove
```

Useful switches: `-InstallDir <dir>` (`mink.exe`'s `bin` directory or its parent),
`-MinkExe <path>`, `-IconPath <ico>`, `-Editor <editor.exe>`, `-Force`, `-Uninstall`. The
script exits 0 on success and 1 on refusal or error, and it is idempotent: repeated runs
produce the same registry state, including repair after manual edits.

From a source checkout the same script runs unchanged from `npm\mink\windows\`.

## 7. Editor integration

**There is no MINK editor extension in this repository, and none was invented.** The
design package's `editor/vscode/package.json.snippet` was inspected and is preserved as
guidance; when a MINK language extension is written, it needs exactly this:

```jsonc
"contributes": {
  "languages": [{
    "id": "mink",
    "aliases": ["MINK", "mink"],
    "extensions": [".mink"],
    "icon": { "light": "./icons/mink-file.svg", "dark": "./icons/mink-file.svg" }
  }]
},
"icon": "icon.png"   // 128x128, from assets/brand/icon/application/png/mink-app-128.png
```

Sources for that step: copy `assets/brand/icon/source-file/mink-file-master.svg` to
`./icons/mink-file.svg` and `assets/brand/icon/application/png/mink-app-128.png` to
`./icon.png`. Until such an extension exists, `.mink` files are handled by Windows' own
Open-with mechanism described above, which is why no editor is assumed or required.

## 8. Web, GitHub and social assets

This repository contains no website, so the design package's `web/favicon/` set is **not**
duplicated here: those files belong to the website project and are derivable from the
application icon (`favicon.ico` there is the 16/32/48 ladder, plus 180/192/512 PNGs and a
web manifest).

Integrated here:

- `README.md` header — `web/github/mink-readme-header-{light,dark}.png` via `<picture>`;
- `web/github/` avatars and `web/social/` preview/profile/docs-header artwork, stored for
  repository and GitHub account use.

Applying them to GitHub is manual and external to this repository: upload
`web/social/mink-social-preview-dark-1280x640.png` under repository *Settings → Social
preview* and `web/github/mink-avatar-dark-500.png` as the account avatar. No script in
this repository changes GitHub settings.

## 9. Production, preview, and what is not here

- **Production:** everything in `assets/brand/` except `previews/`, plus the shipped kit in
  `npm/mink/windows/`.
- **Preview only:** `assets/brand/previews/` — size ladders and an Explorer mock used for
  review; not referenced by any build or distribution step.
- **Not integrated:** the rejected app-icon alternatives
  (`extras/app-icon-alternatives/option-b`, `option-c`), the website favicon set, and the
  redundant copies the design package keeps in `logo/monochrome/`, `windows/png/` and
  `web/favicon/`. Each artwork is stored once, in the directory that owns it; the
  validation script fails if any of those classes reappears.

## 10. Validation

Two permanent, dependency-free checks:

```bash
python validation/brand_assets/verify_brand_assets.py
powershell -ExecutionPolicy Bypass -File validation/windows_filetype/verify_filetype_association.ps1
```

`verify_brand_assets.py` (9 checks) validates the inventory (73 required files), rejects the
non-integrated artwork classes, parses all 49 SVGs as XML with their viewBox and resolves
every internal `url(#id)`/`href="#id"` reference, decodes all 63 PNGs (signature, chunk
CRCs, IDAT length, alpha channel, file-name/dimension agreement), checks both ICOs
(7 frames, 32-bpp, frame dimensions, and frame-for-frame identity with the PNG exports),
confirms the shipped kit copies are byte-identical to the brand tree, and reports whether
`mink.exe` has a resource directory.

`verify_filetype_association.ps1` (56 checks, 11 steps) works in a temporary install tree
whose path contains a space: it snapshots the keys it touches, proves that an association
owned by another application is not taken over without `-Force` and that `-Force`
preserves that application's entries, registers from the package layout alone, and then
asks **Windows** what it resolved — `SHGetFileInfo` for the type name and icon,
`AssocQueryString` for the friendly name, default icon, ProgID and open command. It
verifies that no open command exists (so a source file is never executed), binds a probe
editor and opens the fixture through the association to prove the file reaches the editor
while no compilation happens, re-registers twice in one session, registers from a Unicode
path, uninstalls and confirms that only MINK-owned entries disappeared, and finally
restores the machine's previous state.

`cmd.exe`'s `assoc`/`ftype` are deliberately not used as evidence: they read the
machine-wide (`HKLM`) classes only and cannot see a per-user registration, even though
Explorer resolves it correctly.

## 11. Limitations

1. `mink.exe` has no embedded icon resource; see §3 for the reason and the local procedure.
2. No Windows installer exists, so nothing registers the association automatically on
   install; the user installs it with the shipped script, and the Inno Setup snippet from
   the design package is not shipped (it is for an installer this repository does not have).
3. No MINK editor extension exists; §7 documents the integration path for one.
4. The favicon set is not in this repository because there is no website here.
5. Applying the GitHub avatar and social preview is a manual, external GitHub setting.
6. If another application already owns `.mink` with a class-level `OpenWithProgids` list,
   Windows asks the user to confirm the default application once after a `-Force` takeover;
   that list is not deleted on purpose.
7. The per-user "Open with" choice (`UserChoice`) is owned by Windows and the user. It is
   never written or removed, so a previous manual choice for `.mink` keeps governing until
   the user resets it in *Settings → Default apps*.

## 12. Regenerating artwork

The SVGs are the source of truth: `masters/svg/mink-master.svg` and
`masters/vector/mink-geometry.json` hold the symbol geometry and colours, and
`icon/*/mink-*-master.svg` plus the per-size SVGs (16–128, pixel grids at the small sizes)
produce the PNG frames and ICOs. After regenerating, re-run both validation scripts; the
asset check fails if a frame, dimension, size ladder or duplicate-class file is wrong.
