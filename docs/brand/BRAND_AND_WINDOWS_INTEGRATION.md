# MINK brand assets and Windows file identity

**Status:** implemented, file-type integration closed 2026-11-22 (Session 286) ·
**Version:** 1.0.4 at implementation (unchanged by the 1.0.5 candidate) ·
**Platform:** Windows x86_64
**Design source:** the supplied `MINK UI SETS OFFICIAL` artwork package (2026-10-25), used as
delivered — no artwork was redrawn, recoloured or rescaled.

This page documents what was integrated, where it lives, how the `.mink` Windows file
association is registered and removed, and what is deliberately *not* integrated. The
implementation record with the validation transcript is
[`docs/implementation/SESSION_139_BRAND_ASSETS_WINDOWS_FILE_IDENTITY.md`](../implementation/SESSION_139_BRAND_ASSETS_WINDOWS_FILE_IDENTITY.md).

## 1. Where the artwork lives

| Path | Contents |

## 2. Logo variants

Three colourways exist for every lockup: `-ink` (`#1C1D21`, the default on light
backgrounds), `-white` (for dark backgrounds) and `-black` (`#000000`, for print and
one-colour production). Lockups: primary (stacked), horizontal, compact, symbol and
wordmark; the symbol additionally has an optical-small variant for 64–128 px and a
silhouette variant for 64 px and below. Palette: Ink `#1C1D21`, White `#FFFFFF`,
Fold `#3A3C44`, Edge `#45474F`, Paper `#F4F4F2`.

The horizontal lockup has a minimum width of 96 px / 20 mm and clear space equal to the
wordmark cap-height, already built into the SVG bounds. The README header uses the
supplied 1280x320 PNG pair through a `<picture>` element so it follows the reader's
colour scheme.

## 3. Application icon and `mink.exe`

`assets/brand/windows/ico/mink-app.ico` (shipped as `npm/mink/windows/mink-app.ico`) is
the official application icon: 7 frames — 16, 24, 32, 48, 64, 128 and 256 px — all 32-bpp
PNG-compressed, and each frame is byte-identical to the PNG export it was built from
(`assets/brand/icon/application/png/`).

**`mink.exe` and every program MINK builds now carry this icon (1.0.5).** Cargo builds the
compiler with no crate dependencies and no build script, so a resource compiler (`rc.exe`,
`windres`) was never an option: it would add an external toolchain to a build that
deliberately has none. Instead MINK writes the resources itself. `src/backend/resource.rs`
builds the `.rsrc` section (one `RT_ICON` per frame, the `RT_GROUP_ICON` directory, and an
`RT_VERSION` block) and appends it to a finished PE image, moving no existing address.

- `mink build` does this for every Windows program. The icon is the MINK icon unless you pass
  `--icon <file.ico>` or `--no-icon`. The version strings name the program, and inside a project
  they take the name and version from `mink.toml`. Adding all seven frames costs about 19 KB.
- `mink resource <exe> --icon mink-app.ico --product MINK --version 1.0.5 ...` does the same for
  an executable that has none. A release uses it to brand `mink.exe`. It refuses an executable
  that already has resources instead of replacing them, and it writes a temporary file first
  and then moves it into place, so an interruption never leaves a half-written file. A running
  program cannot be replaced, so the compiler brands a copy of itself, not itself.
- The result is checked against Windows itself: `FileVersionInfo` reports the strings, and
  `ExtractAssociatedIcon` returns the 32 px frame. A string table without `FileVersion` and
  `ProductVersion` showed up empty in Windows, so those two strings are always written.

`mink.rc` stays in the package as a reference for anyone who prefers a resource compiler.

## 4. `.mink` source-file icon

`assets/brand/windows/ico/mink-file.ico` (shipped as `npm/mink/windows/mink-file.ico`)
is the `.mink` source-file icon, distinct from the application icon by design: a document
sheet carrying the mink mark, with the wordmark only in the 128 and 256 px frames. It has
the same 7 frames and is likewise byte-identical frame-for-frame to
`assets/brand/icon/source-file/png/`. A one-colour variant
(`icon/source-file/mink-file-mono.svg`) and a 1024 px PNG are in the brand tree for
editor and print use.

## 5. The `.mink` Windows file association

| Property | Value |
| --- | --- |
| Extension | `.mink` |
| ProgID | `MINK.SourceFile` |
| Display name | `MINK Source File` |
| Content type | `text/x-mink` |
| Perceived type | `text` |
| Default icon | `mink-file.ico` (quoted path, index 0) |
| Default action | **Edit** (Notepad, or the editor given with `-Editor`); never run or build |
| Scope | per-user (`HKCU`), no administrator rights, `HKLM` untouched |

Registry layout written by the script:

| Key | Value |
| --- | --- |
| `HKCU\Software\Classes\.mink` | `(default)` = `MINK.SourceFile`, `Content Type`, `PerceivedType` |
| `HKCU\Software\Classes\MINK.SourceFile` | `(default)` and `FriendlyTypeName` = `MINK Source File` |
| `HKCU\Software\Classes\MINK.SourceFile\DefaultIcon` | `"<install>\mink-file.ico",0` |
| `HKCU\Software\Classes\MINK.SourceFile\shell` | `(default)` = `edit` (or `open` when `-Editor` is given): the double-click verb |
| `...\shell\run`, `check`, `build` | `Run with MINK`, `Check with MINK`, `Build executable`; command `"<install>\mink.exe" shell <verb> "%1"`; `Icon` = `mink-app.ico`; `MultiSelectModel` = `Single` |
| `...\shell\edit\command` | `"<notepad.exe>" "%1"` (not added when an editor is bound; `open` does that job) |
| `...\shell\open\command` | only with `-Editor`: `"<editor.exe>" "%1"`, labelled `Edit` |
| `HKCU\Software\Classes\.mink\ShellNew` | `FileName` = `windows\template.mink` (or `NullFile` when the template is missing) |
| `HKCU\Software\Classes\.mink\PersistentHandler` | the plain-text search filter, as `.txt` uses |
| `HKCU\Software\Classes\.mink\shellex\{8895b1c6-b41f-4c1c-a562-0d564250836f}` | the preview handler read from this PC's `.txt`, so it is right for the Windows version |
| `HKCU\Software\MINK\Capabilities` and `HKCU\Software\RegisteredApplications\MINK` | the Settings > Default apps entry |
| `HKCU\Software\Classes\MINK.SourceFile\MinkOwned` | which of the optional facilities this script added, so uninstall removes exactly those |
| `HKCU\...\Explorer\FileExts\.mink\OpenWithProgids` | `MINK.SourceFile` (REG_NONE), so the type appears in the Open-with list |

**Double-clicking a `.mink` file never compiles or runs it.** The default verb, named by the
`(default)` value of the `shell` key, is `edit`, which opens Notepad. With `-Editor` the default
is `open`, the chosen editor applied to the file with both paths quoted. The right-click verbs
`run`, `check` and `build` only run when the user picks them. They are single-selection, so
selecting several files does not offer them. If the user has already chosen an app in
Windows (`FileExts\.mink\UserChoice`), that choice is Windows' and wins; the script never
writes or removes it. `edit` is always registered when any verb is, because without a named
default Windows would pick the first verb alphabetically, which is `build`.

The verb commands run `mink.exe shell <run|check|build> "<file>"`, a small command that runs
the named action, then waits for Enter when it has a terminal, so Explorer's console window
does not vanish before the output can be read. `mink.exe` is started directly, without
`cmd.exe`, so characters such as `&` or `%` in a file name are never interpreted by a shell.

**Ownership of the extras.** The New-menu entry, the search filter and the preview handler are
only written when `.mink` has none of its own. If another application registered one, it is left
alone and the run says so. The ones this script adds are listed in `MinkOwned`, and `-Uninstall`
removes exactly those.

**Taking `.mink` over from another application.** If another ProgID currently owns
`.mink`, registration refuses and changes nothing until `-Force` is given. `-Force`
records the previous owner in `MINK.SourceFile\PreviousDotMinkOwner` and `-Uninstall`
restores it. A class-level `OpenWithProgids` list created by that other application is
never deleted: while it exists Windows treats the extension as "open with" and asks the
user to confirm the application once, which is the documented shell behaviour.

**Uninstall removes only MINK-owned entries**: the extension's default value only if it is
still `MINK.SourceFile`, the `Content Type`/`PerceivedType` values only if they are the
ones this integration wrote, the `MINK.SourceFile` tree, and the `OpenWithProgids` value
under `FileExts`. Another application's values and subkeys inside `HKCU\Software\Classes\.mink`
are preserved, the `UserChoice` default-app entry is never touched, and an extension key
that is empty afterwards is removed so no debris is left.

**Shell refresh** uses `SHChangeNotify(SHCNE_ASSOCCHANGED, SHCNF_IDLIST, NULL, NULL)` and,
when present, `ie4uinit.exe -show` to rebuild the cached file-type icon. Explorer is never
restarted or killed.

### 5.1 Every MINK file type and its Windows identity

MINK has **exactly one** user-facing file type with its own extension: `.mink`. The other
types that appear in a MINK project are identified by file *name* (or are generated), so
registering them would take over an unrelated extension. This inventory is the complete
set found in the compiler, the package manager, the standard library, `examples/`,
`validation/`, `benchmarks/`, the npm manifests and this documentation:

| Extension | Purpose | Status | Opening application | Windows association | Icon | Registration | Verification |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `.mink` | MINK source: programs, modules (`mod x;` → `x.mink`), the 27 stdlib modules, tests | **supported** | Notepad by default; `-Editor` binds another | `HKCU\Software\Classes\.mink` → `MINK.SourceFile`, content type `text/x-mink`, perceived type `text` | `mink-file.ico` — 7 frames | `register-mink-filetype.ps1` (per-user) | 140-check harness, live registry cycle on this machine, Explorer visual check at 16 px and large-icon view, shell bitmap pixel-compared with the official frame |
| `mink.toml` | Package manifest read and edited by `mink init/add/remove/install/update` (`src/package/manifest.rs`) | **supported** (project metadata) | any TOML/text editor the user chooses | **not registered**, and must not be: the extension is `.toml`, shared with unrelated applications | none — no manifest artwork exists in the brand kit, so none was invented | none | static inspection of `src/package/` and `tests/package_manager.rs`; deliberately outside the association |
| `mink.lock` | Lockfile written by `mink install`/`update` (`src/package/lock.rs`) | **supported, generated** — not hand-edited | text editor | **not registered** (`.lock` is shared) | none | none | same as `mink.toml` |
| `.mink/` | Per-project state directory: installed packages, environment state (`src/package/env.rs`, `STATE_DIR`) | **internal** | not applicable — it is a directory | not applicable | not applicable | not applicable | static inspection |
| `.exe` | Output of `mink build` | **generated artifact** | Windows loader | Windows' own executable type — MINK does not touch it | Windows default executable icon (see §3) | none | not a MINK file type |

Why the manifest and lockfile are not file types of their own: Windows associates by
extension only, so a `.toml` or `.lock` registration would apply to every TOML file and
every lockfile on the machine. `mink.toml` and `mink.lock` are recognised by full name,
which the shell cannot express. No separate icon is defined for them, and no new visual
identity was created for this audit.

### 5.2 How the icon path is resolved (portability)

The registered `DefaultIcon` has to be an absolute path, so the script derives it from the
copy that is running, never from a hard-coded location, the current directory or a
temporary file:

| Invocation | Installation found | Icon used | Evidence |
| --- | --- | --- | --- |
| npm package `<prefix>\node_modules\@p4inz-code\mink\windows` (global or local) | `<package>\bin\mink.exe` | `<package>\windows\mink-file.ico` (the `bin` directory ships no ICO) | harness step 11, temporary package tree whose path contains a space |
| Repository checkout `npm\mink\windows` | `mink.exe` beside the script if present, else on `PATH` | `<script dir>\mink-file.ico` | harness step 12 (no installation at all) and this machine's live association |
| `-InstallDir` / `-MinkExe` | the directory given | `<install>\mink-file.ico`, else the script's own copy | harness steps 5 and 9 (space and Unicode path) |
| `-IconPath <ico>` | not needed | exactly that file | harness step 13 |

Before any registry value is written the resolved file must exist **and** carry a valid
ICONDIR header (reserved 0, type 1, frame count > 0). A missing, empty or malformed icon
makes registration exit 1 with the paths it searched, and the registry is left untouched —
the harness checks that with a from-scratch signature comparison, so an earlier
registration is never silently replaced by a broken one. Because the path is captured at
registration time, re-run the script after moving, upgrading or reinstalling the package;
`-Uninstall` and a fresh run is the supported repair.

**Package requirement.** Only a package that ships `windows/` can resolve the icon from an
installed copy. The published `1.0.4` tarball was downloaded and inspected on 2026-11-22:
28 files, `bin/mink.exe` plus `stdlib/`, `package.json` and `LICENSE`, **no `windows/`**. The
1.0.2 package is the same. `npm pack` in `npm/mink` confirms the 1.0.5 candidate does ship it
(35 files, 5 under `windows/`).
Until 1.0.5 is published, a checkout is the only installation that carries the kit, and
the association on such a machine necessarily points into the checkout. That is a release
dependency, not a defect in the script.

**Why one mechanism.** The design package also contains a `.reg` file and an Inno Setup
snippet. Neither is shipped: a `.reg` file cannot resolve an installation path, so it has
to hard-code one (the supplied reference assumes
`%LOCALAPPDATA%\Programs\MINK\bin`, which this repository does not provide) and it
hard-coded Notepad as the open command; the Inno Setup snippet belongs to an installer
that does not exist. The PowerShell script is the single authoritative mechanism.

## 6. Register and unregister

The shipped package resolves everything from its own location, so any npm prefix, drive
or Unicode path works — but only a package that actually contains `windows/` can be used,
and the published `1.0.4` does not (verified from its tarball: 28 files, no `windows/`).
Until a version shipping the kit is published, run it from a checkout:

```powershell
git clone https://github.com/p4inz-code/mink.git
powershell -ExecutionPolicy Bypass -File .\mink\npm\mink\windows\register-mink-filetype.ps1            # register
powershell -ExecutionPolicy Bypass -File .\mink\npm\mink\windows\register-mink-filetype.ps1 -Uninstall # remove
```

From an installed package that ships the kit:

```powershell
$package = Join-Path (npm root -g) '@p4inz-code\mink'
powershell -ExecutionPolicy Bypass -File "$package\windows\register-mink-filetype.ps1"            # register
powershell -ExecutionPolicy Bypass -File "$package\windows\register-mink-filetype.ps1" -Uninstall # remove
```

Useful switches: `-InstallDir <dir>` (`mink.exe`'s `bin` directory or its parent),
`-MinkExe <path>`, `-IconPath <ico>`, `-Editor <editor.exe>`, `-Verbs run,check,build,edit`,
`-NoContextMenu`, `-NoNewMenu`, `-NoPreview`, `-NoDefaultApps`, `-Quiet`, `-Force`,
`-Uninstall`. The
script exits 0 on success and 1 on refusal or error, and it is idempotent: repeated runs
produce the same registry state, including repair after manual edits.

From a source checkout the same script runs unchanged from `npm\mink\windows\`.

## 7. Editor integration

**There is no MINK editor extension in this repository, and none was invented.** The
design package's `editor/vscode/package.json.snippet` was inspected and is preserved as
guidance; when a MINK language extension is written, it needs exactly this:

```jsonc
"contributes": {
  "languages": [{
    "id": "mink",
    "aliases": ["MINK", "mink"],
    "extensions": [".mink"],
    "icon": { "light": "./icons/mink-file.svg", "dark": "./icons/mink-file.svg" }
  }]
},
"icon": "icon.png"   // 128x128, from assets/brand/icon/application/png/mink-app-128.png
```

Sources for that step: copy `assets/brand/icon/source-file/mink-file-master.svg` to
`./icons/mink-file.svg` and `assets/brand/icon/application/png/mink-app-128.png` to
`./icon.png`. Until such an extension exists, `.mink` files are handled by Windows' own
Open-with mechanism described above, which is why no editor is assumed or required.

## 10. Validation

Two permanent, dependency-free checks:

```bash
python validation/brand_assets/verify_brand_assets.py
powershell -ExecutionPolicy Bypass -File validation/windows_filetype/verify_filetype_association.ps1
```

`verify_brand_assets.py` (9 checks) validates the inventory (73 required files), rejects the
non-integrated artwork classes, parses all 49 SVGs as XML with their viewBox and resolves
every internal `url(#id)`/`href="#id"` reference, decodes all 63 PNGs (signature, chunk
CRCs, IDAT length, alpha channel, file-name/dimension agreement), checks both ICOs
(7 frames, 32-bpp, frame dimensions, and frame-for-frame identity with the PNG exports),
confirms the shipped kit copies are byte-identical to the brand tree, and reports whether
`mink.exe` has a resource directory.

`verify_filetype_association.ps1` (88 checks, 15 steps at the time; 140 checks after the 1.0.5 sprint, see 10.1) works in a temporary install tree
whose path contains a space: it snapshots the keys it touches, proves that an association
owned by another application is not taken over without `-Force` and that `-Force`
preserves that application's entries, registers from the package layout alone, and then
asks **Windows** what it resolved — `SHGetFileInfo` for the type name and icon,
`AssocQueryString` for the friendly name, default icon, ProgID and open command. It
verifies that no open command exists (so a source file is never executed), binds a probe
editor and opens the fixture through the association to prove the file reaches the editor
while no compilation happens, re-registers twice in one session, registers from a Unicode
path, uninstalls and confirms that only MINK-owned entries disappeared, and finally
restores the machine's previous state.

Steps 11–14 were added in Session 286 to cover the gaps an audit found: the real npm
package layout (icon only in `windows\`, none in `bin\`), a source checkout with no
installation present, refusal with the registry provably untouched for a missing, empty or
malformed icon and for a non-existent `-IconPath`, that the registered icon is a valid
7-frame ICO, and that the shipped kit is complete (`windows/` in the npm manifest,
`mink.rc`, `README.md`, both ICOs) while the script declares exactly one extension,
claims no `.toml`/`.lock` type, assumes no drive letter and resolves assets from
`$PSScriptRoot`. Existing assertions were not weakened; the count rose from 56 to 88.

`cmd.exe`'s `assoc`/`ftype` are deliberately not used as evidence: they read the
machine-wide (`HKLM`) classes only and cannot see a per-user registration, even though
Explorer resolves it correctly.

### 10.1 1.0.5 sprint, M3: the extras

The validator now has **140 checks** (it had 88). The 52 new ones cover:

- the double-click default verb is `edit`, and a real double-click on this PC opened Notepad

- each right-click entry's label, command, icon and single-selection setting, and that

- the New-menu template, the search filter, the preview handler (compared with what `.txt` uses
  on the same PC), the Default apps entry and the `MinkOwned` record;
- each option (`-NoContextMenu`, `-NoNewMenu`, `-NoPreview`, `-NoDefaultApps`, `-Verbs`) turning
  its facility off and the rest staying;
- the `check` verb's registered command line, executed with a real compiler: exit 0, header and
  result printed, no `.exe` produced;
- with an editor bound: `open` is the default and no duplicate `edit` entry is added;
- another application's New-menu entry surviving both a `-Force` takeover and `-Uninstall`;
- uninstall leaving none of the extras behind, and the machine returning to its starting state,
  including the `MINK` value under `RegisteredApplications`.

## 11. Limitations

1. `mink.exe` has no embedded icon resource; see §3 for the reason and the local procedure.
2. No Windows installer exists, so nothing registers the association automatically on
   install; the user installs it with the shipped script, and the Inno Setup snippet from
   the design package is not shipped (it is for an installer this repository does not have).
   Because the registered `DefaultIcon` is an absolute path captured at registration time,
   moving, upgrading or reinstalling the package requires re-running the script; nothing
   repairs the path automatically.
3. Distribution beyond a checkout depends on a package that ships `windows/`. Publishing
   1.0.5 is an owner-authorized release action and has not happened; the registry serves
   1.0.4, whose tarball was inspected on 2026-11-22 and has no `windows/`, so an
   association can only be created from a checkout today. The upgrade path is
   `npm install -g @p4inz-code/mink@1.0.5`, then re-run the registration script from the
   package (§5.2).
4. No MINK editor extension exists; §7 documents the integration path for one.
5. The favicon set is not in this repository because there is no website here.
6. Applying the GitHub avatar and social preview is a manual, external GitHub setting.
7. If another application already owns `.mink` with a class-level `OpenWithProgids` list,
   Windows asks the user to confirm the default application once after a `-Force` takeover;
   that list is not deleted on purpose.
8. The per-user "Open with" choice (`UserChoice`) is owned by Windows and the user. It is
   never written or removed, so a previous manual choice for `.mink` keeps governing until
   the user resets it in *Settings → Default apps*.

## 12. Regenerating artwork

The SVGs are the source of truth: `masters/svg/mink-master.svg` and
`masters/vector/mink-geometry.json` hold the symbol geometry and colours, and
`icon/*/mink-*-master.svg` plus the per-size SVGs (16–128, pixel grids at the small sizes)
produce the PNG frames and ICOs. After regenerating, re-run both validation scripts; the
asset check fails if a frame, dimension, size ladder or duplicate-class file is wrong.
